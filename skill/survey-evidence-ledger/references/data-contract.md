# Data contract

Map an existing project into these logical entities; retain its stable identifiers when possible.

| Entity | Required semantics |
|---|---|
| work | Canonical intellectual work; title alone is not identity. |
| source | Exact manifestation, URL/local identity, observed version, locator and representation type. |
| role claim | Body-supported contribution, task or scope statement plus limits. |
| configuration | One concrete system boundary and update/evaluation protocol. |
| relation | Typed directed edge with evidence at both endpoints and a bounded meaning. |
| branch | Curator grouping and reading route; grouping does not imply ancestry. |
| module | Reader question, bounded answer, evidence references, comparison dimensions and gaps. |
| manifest | Release version, input hashes, output hashes, counts, checks and publication state. |

Keep these states distinct:

- inventory, screened, source available, primary passage reviewed;
- navigation/context, admitted role claim, admitted configuration, admitted relation;
- fixed-corpus synthesis complete, exhaustive primary review, global frontier review;
- local candidate, owner-approved public release.

For incremental updates, maintain reverse dependencies from claim, configuration and work IDs to branches, modules, questions and exported views. Recompute only affected consumers, then verify global referential integrity and regenerate the manifest.

Raw source bytes, extracted passages and private cache locations are provenance inputs. Public exports normally contain stable identifiers, bounded project-authored claims, versions, locators and external links.

The portable lifecycle and answer packet are defined in `method/workflow.json` in the distribution. A new-domain adapter is generated by `scripts/init_domain.py` within the Skill. Domain role fields may vary; generic identity, version and citation semantics do not.
